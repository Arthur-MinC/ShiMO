## 二、背景与问题

### 2.1 现状

Live2D 模型在安卓游戏中广泛用于角色立绘。游戏运行时从安装目录加载三类资源：模型本体 `.moc3`、清单文件 `.model3.json`、以及它引用的纹理图集、动作、表情、物理配置。这些文件在磁盘上是一个**不可分割的整体**——路径全部相对于 `.model3.json`，单独拿走任何一份都无法使用。

当前想要查看这些模型的人，走的是这样一条路：在模拟器里翻游戏安装目录 → 用文件管理器把整个文件夹拷出来 → 传到 PC → 手动打开 Cubism Editor 逐个尝试加载。这条路有三个断点：

1. **找不到目录**。用户不知道模拟器装在哪、游戏资源在哪个路径下，只能靠教程里抄来的字符串碰运气。
2. **找不全文件**。资源散落在多个子目录，靠肉眼挑选必然漏件，而漏件在 PC 上打开时才会暴露，报错信息还看不出缺了什么。
3. **带不走**。安卓 11 起 `/sdcard/Android/data` 对普通应用完全封闭，模拟器内的文件管理器同样受限制。

### 2.2 问题定义

本项目要解决的核心问题是：**把「从模拟器中找到并取出一份完整可用的 Live2D 运行时包」这件事，从一次高风险的手工作业，变成一次三步以内的确定性操作。**

三个子问题按依赖顺序排列：先解决「连得上」（进程与端口发现），再解决「认得全」（资源聚合与完整性校验），最后解决「带得走」（导出到 PC 并直接打开）。

### 2.3 关键前提

本工具走 **ADB 通道**读取模拟器文件系统，而不是解析模拟器的磁盘镜像。原因：模拟器系统盘是 vmdk / img 格式，直接解析需要处理分区表与 ext4，且只能读取未运行的实例。ADB 通道不受镜像格式影响，代价是要求实例处于运行状态。相比之下代价更小。

同时必须明确：ADB 通道绕开了 Android 11 对**普通应用**的存储封锁（`adb shell` 以 shell 用户运行，权限高于普通应用），但**并未绕开全部限制**——`/sdcard/Android/data` 下的内容在 shell 中仍可能受限，需要 `adb root` 提权。这条边界决定了错误处理的设计。

## 三、产品定位与目标

### 3.1 一句话定义

一款 Windows 桌面工具：自动发现本机安卓模拟器，通过 ADB 扫描目标游戏目录，把散落的 Live2D 运行时文件聚合成完整模型包，导出到本地磁盘后直接调用 Cubism Editor 打开。

### 3.2 目标用户

| 用户类型 | 特征 | 核心诉求 |
|---|---|---|
| 模型制作者 / 二创作者 | 需要参考或改建游戏模型，熟悉 Live2D 但不熟安卓 | 一次拿到完整包，能直接打开 |
| 游戏美术 / 技术美术 | 做画风与动画参考，要求数据对得上官方 | 完整性可信，缺件要提前告警 |
| 开发者 | 需要批量导出做数据集或工具链集成 | 支持多选批量、路径可预测、可脚本化 |

### 3.3 非目标（明确不做）

- **不做 `.moc3` 反向工程**。`.moc3` 是编译产物，无法还原为 `.cmo3` 工程文件，本工具不承诺也不尝试。
- **不做在线资源下载**。工具只处理本机已安装的游戏资源，不提供 APK / OBB 下载。
- **不做模型编辑器**。查看与编辑一律交给 Cubism Editor，本工具只负责「把文件放到正确的位置、以正确的结构」。
- **暂不做 macOS 版本**。首版仅 Windows，与 Cubism Editor 的主要使用环境对齐。

## 四、名词定义

| 术语 | 定义 |
|---|---|
| 运行时包 | 一个 `.model3.json` 及其引用的 `.moc3`、纹理图集、动作、表情、物理配置构成的完整集合。**是本工具的处理单位** |
| 明文资源 | 直接以 `.model3.json`、`.moc3` 等原扩展名落在文件系统上的资源 |
| 容器资源 | 资源被打包进 `.obb`、`.zip`、AssetBundle（`.unity3d` / `.ab`）或自定义加密文件中的形态 |
| 聚合 | 以 `.model3.json` 为锚点，沿其引用关系把散落文件收拢为一个运行时包的过程 |
| 完整性校验 | 检查包内声明引用的文件是否全部存在且非空 |
| 残留包 | 完整性校验未通过的包。默认不勾选导出，但在列表中显式可见 |
| moc3 | 指 `.moc3` 文件，Live2D 模型的编译产物，无法反编译回 `.cmo3` 工程 |

## 五、用户流程

### 5.1 主流程（4 步）

```
① 连接模拟器  →  ② 扫描资源（含进度反馈）  →  ③ 查看结果并勾选  →  ④ 导出并打开
```

### 5.2 用户场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| S-01 | 首次使用，模拟器已运行，游戏已安装 | 软件自动列出模拟器实例，用户点「开始扫描」即可 |
| S-02 | 用户不清楚资源在哪个目录 | 默认扫描 `/sdcard/Android/data` 与 `/sdcard/Android/obb`，无需用户输入 |
| S-03 | 从 15 个包中挑 4 个导出 | 表格可横向比对完整性，残包默认不勾选，勾选数实时汇总体积 |
| S-04 | 导出后要立刻查看模型 | 应用能直接调起本机 Cubism Editor，并明确提示打开 `.model3.json` 而非 `.moc3` |
| S-05 | 扫描结果为空 | 界面给出诊断性解释（发现了什么容器、为什么没命中），而非空表格 |
| S-06 | 遇到无法解包的加密容器 | 逐项列出失败原因，主按钮为「用已解包内容继续」 |
| S-07 | 模拟器未运行 | 实例列表中标注「未运行」，给出启动引导 |
| S-08 | 扫描中途想取消 | 提供取消入口，且明确告知未完成部分不会写入磁盘 |

## 六、功能需求

优先级定义：**P0** = 首发必须；**P1** = 首发应有，可降级；**P2** = 后续版本。

### FR-01 模拟器实例发现与连接（P0）

**描述**：无需用户输入任何路径，自动列出本机可用的模拟器实例。

**处理逻辑**：

1. 枚举本机进程，按进程名与安装目录特征匹配已知模拟器（MuMu、雷电、夜神、逍遥、BlueStacks）。
2. 对匹配到的模拟器目录，按文件名模糊匹配递归查找其自带 adb 可执行文件（候选名包括 `adb.exe`、`HD-adb.exe`、`adb_server.exe`、`nox_adb.exe`，**禁止硬编码单一文件名**）。
3. 使用该模拟器自带的 adb 执行 `adb devices` 获取实例列表，并解析 `127.0.0.1:<端口>` 与 `emulator-<端口>` 两类地址。
4. 对每个实例读取 Android 版本、是否已 root、是否可写 `adb shell`。

**输出**：实例列表，每项含名称、实例标识、ADB 地址、Android 版本、运行状态、root 状态。

**验收要点**：

- 模拟器处于运行状态时，实例应被自动列出且可直接连接，无需用户填写端口。
- 多开场景下，同一模拟器的全部实例都应被列出（注意：MuMu 12 与 BlueStacks 的多开端口无固定递增规律，不得依赖端口推算）。
- 未运行的模拟器应出现在列表中并标注状态，点击时给出启动引导而非报错。
- 实例为已 root 但 ADB 未提权时，应给出 `adb root` 引导。

### FR-02 扫描范围配置（P0）

**描述**：用户可指定要扫描的目录范围，默认覆盖常见位置。

**默认勾选项**：`/sdcard/Android/data`、`/sdcard/Android/obb`。

**可选输入**：用户自定义路径；提供「从已安装应用中选择」入口，通过 `adb shell pm path <包名>` 列出应用及其 APK 路径，辅助用户定位。

**验收要点**：

- 路径归一化：`/sdcard`、`/storage/emulated/0` 等价路径必须去重，同一目录不得扫描两次。
- 路径列举必须走字节流 + 显式 UTF-8 解码通道，保证中文与日文目录名不乱码。

### FR-03 资源扫描与进度反馈（P0）

**描述**：遍历目标目录，识别并聚合运行时包，全过程有明确进度反馈。

**处理逻辑**：

1. 分五个阶段执行并在界面显式呈现：探测模拟器实例 → 拉取应用清单 → 遍历资源目录 → 聚合运行时包 → 完整性校验。
2. 遍历阶段实时上报：整体百分比、当前目录绝对路径、已扫描文件数、已匹配文件数、已聚合包数。
3. 发现容器资源（`.obb` / `.zip` / `.unity3d` / `.ab` / 疑似加密文件）时，计入统计但不中断扫描。

**验收要点**：

- 界面必须同时显示**整体百分比**与**当前正在遍历的目录路径**。仅有不确定进度的旋转图标视为不达标——用户判断程序是否卡死的唯一依据是路径与计数在变化。
- 支持取消。取消后已扫描内容不得写入磁盘，且该承诺需在界面上明示。
- 扫描过程为只读，不得对模拟器内任何文件执行写操作。

### FR-04 运行时包聚合（P0）

**描述**：以 `.model3.json` 为锚点，沿引用关系收拢全部依赖文件。

**处理逻辑**：

1. 扫描阶段收集全部 `.model3.json` 路径。
2. 解析清单文件，提取其引用的 `.moc3`、纹理图集、`motions/*.motion3.json`、`expressions/*.exp3.json`、`physics3.json`、`pose3.json`、`cdi3.json`。
3. 按相对路径解析引用，建立「包 → 文件集合」的映射。
4. 体积统计以包内全部文件的实际大小求和。

**验收要点**：

- 孤立存在的 `.moc3`（找不到对应清单）**不进结果列表**，但需计入日志，便于排查。
- 清单中的路径为相对路径，解析基准必须是 `.model3.json` 自身所在目录。
- 同一文件被多个包引用时不得重复计入体积总和。

### FR-05 完整性校验（P0）

**描述**：在手机端就判断出包是否完整，避免用户在 Cubism Editor 中才发现问题。

**校验项**（按严重度分级）：

| 级别 | 校验内容 | 处理 |
|---|---|---|
| 错误 | 清单中引用的 `.moc3` 不存在 | 标记为残留包，默认不勾选 |
| 错误 | 清单中引用的纹理图集不存在 | 标记为残留包，默认不勾选 |
| 警告 | 无 `motions/` 或无动作文件 | 标记为「无动作」，默认不勾选 |
| 警告 | 无 `expressions/` | 标记为「无表情」，仍可勾选 |
| 提示 | `.moc3` 版本字段高于本机 Cubism Editor 支持范围 | 在导出完成页给出兼容性提示 |

**验收要点**：

- 每个包的状态列需直接显示校验结果（完整 / 缺纹理 / 缺 moc3 / 无动作），而非统一显示「有风险」。
- 校验结果需写入导出目录的 `manifest.txt`，便于事后追溯。
- `.moc3` 版本检测实现方式：读取文件头版本字段。旧版 Cubism Core 加载新版 `.moc3` 时 `csmReviveMocInPlace` 会返回 NULL，且不给出可读原因，因此**必须在导出前拦截**。

### FR-06 结果列表与筛选（P0）

**描述**：以表格形式呈现聚合结果，支持按完整性与来源筛选。

**列定义**：勾选框、模型名、内容构成（动作数 / 表情数）、体积、状态。

**筛选维度**：全部、完整、缺文件、无动作、按来源包名。

**验收要点**：

- 完整包默认勾选，残留包默认不勾选但在状态列以警示色标出。
- 底部实时汇总「已选 N 个包 · 合计体积」，且该数字必须与勾选项体积之和严格一致。
- 桌面端使用表格而非卡片列表——用户在此处需要横向比对多个包的完整性状态。

### FR-07 导出与另存为（P0）

**描述**：把勾选的运行时包按原目录结构写入用户指定位置。

**默认保存位置**：`D:\Live2D\<来源标识>\`，允许用户通过目录选择器更改。

**导出目录结构**（必须原样保持）：

```
<导出根目录>\<来源包名>\
├── manifest.txt                 记录来源、校验结果、导出时间、工具版本
└── <模型名>\
    ├── <模型名>.model3.json     入口清单，Cubism Editor 打开这个
    ├── <模型名>.moc3
    ├── <模型名>.physics3.json
    ├── <模型名>.pose3.json
    ├── <模型名>.cdi3.json
    ├── <模型名>.2048\texture_00.png
    ├── motions\*.motion3.json
    └── expressions\*.exp3.json
```

**验收要点**：

- 相对路径必须原样保持。整个文件夹必须一起移动，单独拷贝 `.moc3` 无意义。
- 文件名含日文或特殊字符时不得转码、不得替换。若目标文件系统不支持，应报错并提示更换位置，而非静默改名。
- 导出前检查目标磁盘剩余空间，不足时提前拦截。
- 导出过程中断（磁盘满、权限、模拟器掉线）后重试，应能识别已完成的包并跳过。

### FR-08 一键调用 Cubism Editor（P0）

**描述**：导出完成后，直接调起本机 Cubism Editor 打开所选模型。

**处理逻辑**：

1. 通过注册表与常见安装路径探测本机 Cubism Editor 安装位置。
2. 以命令行参数方式传入目标 `.model3.json` 路径。
3. 未检测到 Cubism Editor 时，降级为「打开文件夹」并给出下载指引。

**验收要点**：

- 传入的必须是 `.model3.json`，不是 `.moc3`。界面上需以文字明确这一点。
- 同时提供「打开文件夹」与「复制路径」两个兜底动作。
- 若检测到 `.moc3` 版本高于本机 Editor 支持范围，在调起前给出提示。

### FR-09 容器资源处理（P1）

**描述**：识别压缩容器并尝试标准解包。

**分级策略**：

| 容器类型 | 处理 |
|---|---|
| `.zip` / `.obb`（标准 zip 结构） | 尝试自动解包，解包后重新聚合 |
| AssetBundle（`.unity3d` / `.ab`） | **本版不支持**，如实标注并给出建议工具链 |
| 自定义加密容器（文件头不匹配任何已知格式） | **本版不支持**，如实记录文件头特征写入诊断报告 |

**验收要点**：

- 遇到不支持的容器时，**禁止静默返回空结果**。必须列出已发现的容器、大小、格式判断。
- 必须明确说明本版能力边界（明文资源 + 标准 zip/obb），避免用户误判为软件故障。

### FR-10 异常与错误处理（P0）

**描述**：覆盖扫描与导出全链路的异常态。

| 编号 | 异常 | 界面处理 |
|---|---|---|
| E-01 | 扫描结果为空 | 展示诊断页：已发现的容器清单 + 格式判断 + 分级能力说明 |
| E-02 | 容器解包失败 | 逐项列出失败容器与具体原因，主按钮为「用已解包内容继续」 |
| E-03 | 模拟器掉线 | 暂停扫描，保留已有结果，提示重连后可继续 |
| E-04 | 磁盘空间不足 | 在导出前拦截，显示所需空间与可用空间 |
| E-05 | 权限不足（Permission Denied） | 提示 `adb root` 引导；仍失败时如实说明厂商可能锁定 SELinux 策略 |
| E-06 | 目标路径不可写 | 提示更换位置，保留用户已做的勾选 |

**验收要点**：

- 错误信息必须包含**具体对象**（哪个文件 / 哪个容器）与**具体原因**，禁止「部分资源处理失败」这类无法行动的表述。
- 解包失败态的主操作是「用已解包内容继续」，而非「重试」——加密容器重试不会成功，而成功解出的部分才是用户的真实收益。

## 七、非功能需求

### 7.1 性能

| 指标 | 要求 |
|---|---|
| 冷启动到实例列表可见 | ≤ 3 秒（不含模拟器自身响应时间） |
| 扫描进度刷新频率 | ≥ 每 500 毫秒一次，保证用户可感知进度在变化 |
| 万级文件目录扫描 | 不得出现界面无响应；扫描须在独立线程执行 |
| 导出吞吐 | 受 ADB 通道限制，需显示实时速度与剩余时间估算 |

### 7.2 兼容性

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10 1809 及以上 |
| 模拟器 | MuMu 12、雷电 9、夜神、逍遥、BlueStacks 5 |
| Cubism Editor | Cubism 3 / 4 / 5 均可调用；兼容性提示基于 `.moc3` 版本字段 |
| ADB | 优先复用所连模拟器自带版本，找不到时回退内置版本，并在状态栏显示当前使用哪一个 |

> **重要约束**：不得混用不同模拟器的 adb 可执行文件。不同版本会互相抢占端口并将对方实例踢下线，且报错信息完全不体现该原因。

### 7.3 可用性

- 界面文案全中文，禁止英文 slug 泄漏到 UI。
- 所有破坏性操作（覆盖已有目录）需二次确认。
- 扫描与导出过程均有取消入口。

### 7.4 安全与合规

- 工具对模拟器文件系统**只读**，不修改游戏安装目录内的任何内容。
- 导出内容为用户本机已安装游戏中的美术资源，工具本身不提供资源、不提供下载。
- 不内置任何解密算法，不绕过任何加密保护。

## 八、风险与依赖

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R-01 | **游戏资源普遍打包在 AssetBundle 中** | 明文扫描在主流游戏上可能命中率很低，产品价值被质疑 | 明确能力边界；AssetBundle 支持列为独立里程碑；空结果页给出替代工具建议 |
| R-02 | AssetBundle 提取需附带 Unity 动画 → `motion3.json` 的格式转换 | 这是一个独立模块量级的工作，非功能点 | 单独立项评估，不塞进 MVP |
| R-03 | 不同游戏资源路径规则差异大 | 默认扫描范围可能覆盖不到 | 提供「从已安装应用中选择」与自定义路径；扫描日志可视化 |
| R-04 | 模拟器版本升级导致 adb 行为变化 | 连接层失效 | adb 调用层做版本探测与降级；状态栏暴露当前 adb 版本 |
| R-05 | Android 后续版本进一步收紧 shell 权限 | 部分目录不可读 | 错误态已按 E-05 设计；持续跟进 |
| R-06 | 依赖 Cubism Editor 存在性 | 无 Editor 时最后一环断裂 | 已设计降级路径（打开文件夹 + 复制路径） |

**外部依赖**：安卓模拟器客户端、ADB（模拟器自带或 platform-tools）、Live2D Cubism Editor（可选，用于查看）。

## 九、验收标准

### 9.1 功能验收

1. 在装有 MuMu 12 且实例处于运行状态的机器上打开应用，3 秒内列出该实例及其 ADB 地址，无需任何手动输入。
2. 选择默认扫描范围执行扫描，全过程可看到百分比与当前目录变化，任意时刻可取消。
3. 扫描完成后，结果表格中每个包的状态列与其实际缺件情况一致；随机抽取一个标为「完整」的包人工核对，文件集合确实完整。
4. 勾选若干完整包执行导出，导出目录结构与 FR-07 定义严格一致，`manifest.txt` 内容与实际导出内容一致。
5. 点击「用 Cubism Editor 打开」，Cubism Editor 启动并成功加载所选模型。
6. 构造一个必然缺纹理的包，确认它被标为残留、默认不勾选、且不出现在导出结果中。

### 9.2 异常验收

7. 对一个明文资源为零的游戏执行扫描，界面显示诊断页而非空列表，且诊断页中列出的容器与实际磁盘内容一致。
8. 构造一个解包失败的容器，确认失败项逐条列出具体原因，且主按钮为「用已解包内容继续」。
9. 扫描过程中关闭模拟器，确认应用不崩溃、已有结果保留、并给出可读提示。
10. 在剩余空间不足的磁盘上导出，确认在写入前被拦截。

### 9.3 非功能验收

11. 扫描 10,000 个文件的目录，界面保持响应，进度持续刷新。
12. 导出包含日文模型名的包，文件名在 Windows 资源管理器中显示正常，无乱码、无替换。
13. 全程网络与 UI 文案无英文 slug。

## 十、里程碑建议

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| M1 · 连接层 | 模拟器发现、adb 复用、实例列表、权限探测 | FR-01、FR-02 验收通过 |
| M2 · 扫描与聚合 | 五阶段扫描、进度反馈、运行时包聚合、完整性校验 | FR-03、FR-04、FR-05 验收通过 |
| M3 · 导出与打开 | 结果表格、导出、目录结构、Cubism Editor 调用 | FR-06、FR-07、FR-08 验收通过 |

## 十一、附录

### 11.1 已核实的外部事实

| 事实 | 来源 |
|---|---|
| 模拟器默认 ADB 端口：MuMu 12 `16384`、MuMu 6/X `7555`、雷电 9 `5555` 或 `emulator-5554`、夜神 `62001`、逍遥 `21503`、BlueStacks 5 `5555` | 社区实践汇总（多源交叉一致） |
| 多开端口规律：雷电自 5555 起逐个 +2；夜神自 62025 起递增；**MuMu 12 与 BlueStacks 无固定规律** | 同上 |
| 模拟器自带 adb 文件名可能为 `adb.exe` / `HD-adb.exe` / `adb_server.exe` / `nox_adb.exe` | 同上 |
| Android 11 起 `/sdcard/Android/data` 与 `/sdcard/Android/obb` 对普通应用不可读写 | 官方存储策略变更说明 |
| `adb shell` 以 shell 用户运行，权限高于普通应用，但该目录下内容仍可能受限 | 社区实践 |
| 旧版 Cubism Core 加载新版 `.moc3` 时 `csmReviveMocInPlace` 返回 NULL，且无可读原因 | Live2D 官方文档 |
| 新版 Core 向后兼容全部历史 `.moc3` 版本，反之不行 | Live2D 官方文档 |
| Cubism 4.2 格式模型需 Cubism SDK R5 beta1 或更高版本 | Live2D 官方社区 |
| 导出时可选择「SDK3.0 / Cubism3.0(3.2) 支持」以兼容旧 SDK | Live2D 官方文档 |
