关键设计决策

1. 不要求用户知道模拟器装在哪

这是和手机方案最大的区别。模拟器都开着自己的 ADB 端口（MuMu 16384、雷电 5555、夜神 62001、逍遥 21503），软件扫端口和进程即可列出实例。用户点一下就行，不用去翻安装目录。

2. 走 ADB 而不是读磁盘镜像

模拟器的系统盘是 vmdk / img 镜像，直接解析需要处理 ext4、分区表，还只能读未运行的实例。走 ADB 则不管模拟器开没开、镜像什么格式都能拿，代价只是要求实例处于运行状态——所以列表上要标清「运行中 / 未运行」。

3. 用模拟器自带的 adb.exe

不同模拟器的 ADB 版本不同，混用会互相抢占端口把对方踢掉，报错还特别难懂。软件应优先复用所连模拟器目录下的 adb，找不到再回退到内置版本，并在状态栏显示当前用的是哪一个。

4. 表格而不是卡片列表

桌面端屏幕宽，用户在结果页要横向比对「哪些包是残的」。模型名、内容构成、体积、状态排成列，扫一列状态就知道该跳过谁。手机端才需要卡片堆叠，这里不需要。

5. 默认已勾选完整包，残包不自动勾

完整性校验的结果直接决定勾选状态：完整的包默认选中，缺文件的默认不选但在列表里标出来。用户不用逐个判断，也知道自己漏了什么——底部的「已选 4 个包 · 65.9 MB」随时对得上。

6. 收口在一键打开

Cubism Editor 就在同一台机器上，所以最后一步不该是「告诉你文件在哪」，而是直接把 Cubism Editor 调起来。同时兜底给出「打开文件夹」和「复制路径」，并明确提示要选 .model3.json 而非 .moc3。

7. 进度态给「当前目录」，不给转圈

用户判断程序有没有卡死的唯一依据，是路径和计数在变。所以进度页必须同时呈现三样东西：整体百分比、正在遍历的具体路径、以及已聚合的包数量。只放一个不确定进度的旋转图标，用户 30 秒后就会以为死了，然后强杀进程。

另外把五个阶段（探测 → 拉清单 → 遍历 → 聚合 → 校验）显式列在侧栏。大目录扫描动辄几分钟，让用户知道还剩几步，比让他盯着进度条干等体验好得多。

8. 空结果必须解释，不能给一张空表

扫描器返回 0 个包时，如果界面上只有一张空表格，用户的第一反应是「这软件坏了」，然后卸载。空结果本质上是一个信息发现：扫到 3 个压缩容器、1 个疑似加密头，这些都必须报出来。

所以空态页承担的是诊断职责——列出已发现的容器及其格式判断，再给一条分级的能力边界说明：标准 zip / obb 能自动解包，自定义加密容器暂不支持。用户据此就知道该换工具还是换目录。

9. 解包失败的下一步是「继续」，不是「重试」

加密容器解不开，重试一百次还是解不开。所以失败态的主按钮是「用已解包内容继续」——3 个容器里成功的那 1 个已经是 12 个可用模型包，把它导出去才是用户真正要的。

失败项逐条列出具体原因（未知压缩格式 / 自定义加密头 0x4C32），并在同一页写清「已写入诊断报告」。含糊的「部分资源处理失败」会让用户在群里问一圈还得不到答案。

技术实现要点

最大的不确定性：游戏资源往往不是明文的

扫描器按扩展名找 .model3.json 只在明文资源的情况下成立。相当一部分游戏把 Live2D 资源打进 AssetBundle、.obb、zip 或自定义加密容器，此时扫不到任何东西，用户会以为是软件坏了。

建议的应对顺序：① 先做明文扫描，覆盖资源确实直接落盘的游戏；② 检测到 .obb / .zip 时提示「发现压缩资源包」并尝试标准解包；③ AssetBundle 与加密容器作为后续能力，界面上如实告知不支持，别静默返回空结果。

⚠️ 勘误（2026-09-16，PRD 研究阶段发现）：本稿此前把「碧蓝航线」列为明文落盘的代表案例，这是错的。该游戏的 Live2D 资源虽然位于可访问的 Android/data/com.bilibili.azurlane/files/AssetBundles/live2d/ 下，但文件本体是 AssetBundle（.unity3d），按 .model3.json 扩展名扫描会一个都扫不到，需经 UABE / AssetStudio 解析并附带 Unity 动画 → motion3.json 的格式转换。因此「明文扫描能覆盖多少游戏」必须在首发前逐款实测确认，不能按直觉假设。详见 PRD 的风险项 R-01。

这条能力边界直接决定了上面两个异常态长什么样：态 A（空结果）要能说清「扫到了什么容器、为什么没命中」，态 B（解包失败）要能逐项列出哪个容器、失败在哪一步。两个态的代码量加起来不比主流程小，排期时别按边缘情况估。

导出结构（必须原样保持）

D:\Live2D\pjsk_extract\<包名>\
├── manifest.txt                 记录来源、校验结果、导出时间
└── <模型名>\
    ├── <模型名>.model3.json    ← 入口清单，Cubism Editor 打开这个
    ├── <模型名>.moc3           ← 编译产物，无法反编译回 .cmo3
    ├── <模型名>.physics3.json
    ├── <模型名>.pose3.json
    ├── <模型名>.cdi3.json
    ├── <模型名>.2048/texture_00.png
    ├── motions/*.motion3.json
    └── expressions/*.exp3.json

路径全部相对于 .model3.json，整个文件夹必须一起移动，单独拷一个 moc3 出来毫无意义。模型名常含日文与特殊字符，注意目标文件系统的编码。导出时选的 SDK 版本需与打开用的 Cubism Editor 支持范围一致，否则会被直接拒绝加载。
